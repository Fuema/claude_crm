# Architecture

Read this before creating a feature, adding a folder, moving code, or
deciding whether code runs on the server or in the browser.

## Big Picture

```
Browser ──(SSR HTML, then RPC calls)──▶ Cloudflare Worker (TanStack Start)
                                          ├─ route loaders + server functions
                                          ├─ Better Auth  (/api/auth/*)
                                          ├─ Prisma ──▶ Neon PostgreSQL
                                          ├─ Upstash Redis (rate limit, idempotency)
                                          ├─ R2 (files), Queues (outbox events),
                                          │  Durable Objects (real-time)
                                          └─ Cron Trigger (outbox relay)
```

One codebase, one deployable Worker. The UI never calls the database or a
third-party service directly: it calls **server functions**, which run only
on the server.

## Feature Folder Layout

Every feature follows the reference feature named in `docs/project.md`
(`features/customers/`):

```
features/customers/
├── server/            SERVER ONLY
│   ├── customer-functions.ts   createServerFn definitions (the feature's "API")
│   ├── customer-service.ts     Business logic + Prisma queries; takes (db, input)
│   └── customer-service.test.ts Integration tests against the test database
├── types/             Models and Zod schemas shared by server and client
│   ├── customer.ts             Model type returned to the client
│   └── customer-schemas.ts     Input schemas (create, update, list search)
├── hooks/             Query key factory, TanStack Query hooks calling the server functions
├── components/        UI used only by this feature
├── pages/             Page components rendered by route files
├── store.ts           Optional TanStack Store for feature-only UI state
└── index.ts           Public API: the ONLY file other code may import
```

- **`*-functions.ts`** is thin: declare the function, attach middleware,
  validate input with the Zod schema from `types/`, call the service, return
  a model. No queries here.
- **`*-service.ts`** holds the rules (`CUSTOMER_ARCHIVED`, `NAME_TAKEN`, …) and
  the queries. It receives a tenant-scoped db, so it is easy to test without
  HTTP.
- **`types/`** must not import from `server/`, Prisma, or anything
  server-only: the client imports it.
- `index.ts` exports pages, hooks, types, and **server functions** (calling a
  server function from the client is safe: the bundler replaces its body with
  an RPC stub). It never exports a service.

## The Server/Client Boundary

| Code                                              | Runs on                                                |
| ------------------------------------------------- | ------------------------------------------------------ |
| `createServerFn(...).handler(...)` body           | Server only                                            |
| `src/server/**`, `features/*/server/*-service.ts` | Server only                                            |
| Server routes in `routes/api/`                    | Server only                                            |
| Route `loader` / `beforeLoad`                     | **Both** (server on first load, browser on navigation) |
| Components, hooks, stores                         | Both (SSR) — treat as client code                      |

Rules:

- A loader or `beforeLoad` never touches Prisma or secrets directly. It calls
  a server function.
- Only server functions, server routes, and `src/server/` may import
  `src/server/**`, a `*-service.ts`, the Prisma client, or
  `cloudflare:workers`.
- Biome's `noRestrictedImports` (in `biome.json`) fails `bun run check` when
  code outside `src/server/`, `features/*/server/`, and `routes/api/` imports
  `@/server/*`, `@/generated/*`, or `cloudflare:*`.
- After a build, `dist/client/` must not contain Prisma, the Neon driver, or
  `DATABASE_URL`. Check it when touching the boundary.
- Components render on the server first: no `window`, `document`, or
  `localStorage` at render time; use effects.

## Routing (TanStack Router)

- Routes are file-based in `src/routes/`:

```
routes/
├── __root.tsx              Root: HTML shell, providers, router context { queryClient }
├── sign-in.tsx, sign-up.tsx
├── _authenticated.tsx      Layout: beforeLoad requires a session and an active workspace
├── _authenticated/
│   ├── index.tsx           /
│   └── customers/
│       ├── index.tsx       /customers
│       └── $customerId.tsx /customers/:customerId
└── api/
    └── auth/$.ts           Better Auth handler (GET + POST)
```

- **Route files are thin.** They declare the route (`validateSearch`, `loader`,
  `beforeLoad`, error and pending components) and render a page imported from
  the feature's `index.ts`.
- **Search params are typed and validated with Zod** in `validateSearch`.
  A list page's search, filter, sort, and page state lives in the URL.
- **Data loading:** a loader may prefetch with
  `context.queryClient.ensureQueryData(...)` so SSR renders with data;
  components still read through the feature's query hooks.
- **Auth guard:** `_authenticated.tsx`'s `beforeLoad` calls the `getSession`
  server function. No session → redirect to `/sign-in?redirect=…` (validated
  with `isInternalPath`). No active workspace → redirect to workspace
  selection. The guard is for UX only; **every server function checks the
  session again**.
- Features read route state with `getRouteApi('<route id>')`, never by
  importing from `routes/`.
- Code splitting is automatic (`autoCodeSplitting`).

## Dependency Rules

```
routes        → features (index.ts only), components, stores, lib, types
features      → components, hooks, stores, lib, types, server (server/ folder only)
components    → components/ui, lib, types
hooks         → stores, lib, types
stores        → lib, types
server        → lib, types, generated
lib           → (nothing in the app)
```

- `components/` never imports from `features/` and never reads stores.
- A feature never imports another feature's internals; only its `index.ts`.
  A service that needs another feature's data queries it itself (same
  tenant-scoped db) or calls the other feature's exported server function.
- Only `features/*/server/` and `src/server/` touch the database.

Enforced by `noRestrictedImports` overrides in `biome.json`: server-only
imports (see above) and `components/` importing features, stores, or app
hooks. The other rules are checked in review. <!-- TODO: cross-feature
internals (only `index.ts`) once there are two features. -->
